# Publishing KVLite's language bindings

Research date: 2026-09-29. This is a publication plan, **not** evidence that KVLite owns any registry namespace or has a native release. Public registry API checks below identify two existing, unrelated name collisions; a 404 for another name is neither a reservation nor proof of account control. GitHub's environments endpoint returned zero configured environments; listing repository variables and releases returned HTTP 401 here, so confirm those settings in the owner's account. The latest `main` commit checked for this note, `a8706b236b7ebe7ba5f451683f4308ebe5763339`, had successful GitHub **Test** and **Test language bindings** workflows on 2026-09-29; that is test evidence, not publication. `git ls-remote --tags origin 'v*'` returned no release tags.

## What the repository already implements

The repository-root [`go.mod`](../go.mod) is the thin `github.com/webong/kvlite` Go binding. The other package manifests are [`composer.json`](../lib/bindings/php/composer.json) (`kvlite/kvlite`), [`pyproject.toml`](../lib/bindings/python/pyproject.toml) (`usekvlite`, imported as `kvlite`), [`package.json`](../lib/bindings/node/package.json) (`usekvlite`), [`kvlite.gemspec`](../lib/bindings/ruby/kvlite.gemspec) (`kvlite`), and [`Cargo.toml`](../lib/bindings/rust/Cargo.toml) (`usekvlite`, library crate `kvlite`). The npm and Cargo manifests were renamed after the original collision research. These are *thin bindings*; embedded use additionally requires a compatible KVLite host/native engine bundle, as [`lib/bindings/README.md`](../lib/bindings/README.md) describes. Registry package installation by itself does not install a database engine.

[`release-artifacts.yml`](../.github/workflows/release-artifacts.yml) accepts a stable `vX.Y.Z` tag or an explicit `publish_canary` dispatch from `main`. A canary uses `v0.1.0-canary.N`, creates a GitHub prerelease tag after the three native targets and bindings pass, and attaches native and language package artifacts. [`stage-language-bindings.py`](../scripts/stage-language-bindings.py) translates the canary into Python `.devN`, npm/Rust SemVer prereleases, and a RubyGems prerelease without editing source. [`package-language-bindings.sh`](../scripts/package-language-bindings.sh) validates and packages them. Registry jobs remain separately gated by `KVLITE_PUBLISH_PYPI`, `KVLITE_PUBLISH_NPM`, `KVLITE_PUBLISH_RUBY`, `KVLITE_PUBLISH_CRATES`, and `KVLITE_PUBLISH_PHP`; a GitHub prerelease alone is not a registry publish. The PHP mirror additionally needs `KVLITE_PHP_SPLIT_REPO` and `KVLITE_PHP_SPLIT_TOKEN`. Existing GitHub releases are never overwritten. See also the [`binding publication contract`](../lib/bindings/README.md#release-ci).

## Native host and engine bundles: the shared prerequisite

The binding packages do not vendor native storage engines. The release workflow builds a driverless host, LevelDB/BadgerDB/BoltDB/LMDB/RocksDB engine bundles, and HTTP/Redis transport bundles for **linux-amd64, darwin-amd64, darwin-arm64**; then it publishes three tarballs, three SHA-256 sidecars, and `kvlite-installer.sh` as GitHub Release assets. It does not currently build Linux arm64 or Windows. These facts come from [`release-artifacts.yml`](../.github/workflows/release-artifacts.yml) and [`make-release-tarballs.sh`](../scripts/make-release-tarballs.sh), not a confirmed live release. The installer verifies an archive checksum and installed modules; checksums establish integrity, not provenance. See [`install-online.sh`](../scripts/install-online.sh) and [`packaging/README.md`](README.md).

The release workflow now stamps the attached [`installer`](../scripts/install-online.sh) with its concrete release version, so its default download matches [`make-release-tarballs.sh`](../scripts/make-release-tarballs.sh); [`test-install-online.sh`](../scripts/test-install-online.sh) covers that stamped default. The source-tree installer still defaults to `latest` and should be run with an explicit `--version` outside a release. The installer accepts `linux-arm64` despite the missing corresponding release job; reject it clearly or build/test that target before advertising it. GitHub's `releases/latest` URL selects stable releases, not canaries; canary users need their prerelease URL.

## Release gates and honest README claims

1. Reserve and verify the selected `usekvlite` names before any release tag. Public registry APIs show unrelated [`npm kvlite`](https://registry.npmjs.org/kvlite/latest) and [`crates.io kvlite`](https://crates.io/api/v1/crates/kvlite) packages. [`usekvlite` on npm](https://registry.npmjs.org/usekvlite) and [`usekvlite` on crates.io](https://crates.io/api/v1/crates/usekvlite) returned 404 on 2026-09-29 but are unreserved. Public APIs for [`usekvlite` on PyPI](https://pypi.org/pypi/usekvlite/json), [`kvlite` on RubyGems](https://rubygems.org/api/v1/gems/kvlite.json), and [`kvlite/kvlite` on Packagist](https://repo.packagist.org/p2/kvlite/kvlite.json) also returned 404, which only means no public package was returned at check time. The repo's manifests do **not** reserve names.
2. Configure protected GitHub environments (`pypi`, `npm`, `rubygems`, `crates-io`, `packagist`), publisher mappings, and PHP split-repo credentials. Use only the matching opt-in variables after each destination is ready. [GitHub environments](https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment).
3. Validate native archives and notices, especially the bundled RocksDB runtime; do not advertise Linux arm64 until built and tested. Run the existing binding, packaging, and native tests from the canary commit. Each canary gets a new immutable version; registries generally do not permit overwriting it. [Go immutable version guidance](https://go.dev/doc/modules/publishing), [Cargo publication permanence](https://doc.rust-lang.org/cargo/reference/publishing.html).
4. Manually dispatch the first GitHub canary from `main`, inspect its assets, then bootstrap the selected crates.io name (and possibly npm) from validated canary artifacts. Establish a PHP split repo and arrange Packagist registration **after it has a root `composer.json`** (pre-seed a PHP subtree, or register after the first mirror job). Create pending PyPI/RubyGems publishers and enable only ready destinations for a later canary. Inspect each registry and clean consumer installation. A partial multi-registry publish is not atomic: a failed destination needs its own repair/new version plan.
5. Until those checks succeed, the root README may show the **intended** package-manager commands only if visibly marked “not yet released”; it must not imply `pip install`, `npm install`, `gem install`, `cargo add`, `composer require`, or the native installer already work for a general user. A six-language README can be genuinely copy-paste-ready only after both a binding package and its corresponding native host/engine artifact are publicly installable and tested together.
